# `.mmc` format 16: current wire contract

This records the bytes written by the current `marmotc` and read by the current `marmotvm`. It is a baseline for separating their implementations, not a proposal to change the format. All multibyte integers in the artifact container are little-endian. Offsets below are byte offsets from the beginning of the file.

## Header

| Offset | Size | Field | Current meaning |
|---:|---:|---|---|
| 0 | 4 | magic | ASCII `MBC` followed by `00` |
| 4 | 4 | `format_version` (`u32`) | Exactly `16` |
| 8 | 2 | Marmot major version (`u16`) | Written from the producer version; informational to the current reader |
| 10 | 2 | Marmot minor version (`u16`) | Informational |
| 12 | 2 | Marmot patch version (`u16`) | Informational |
| 14 | 2 | reserved (`u16`) | Writer emits zero; current reader does not validate it |
| 16 | 4 | flags (`u32`) | Bit 0 means embedded source files follow the native libraries |
| 20 | 8 | payload size (`u64`) | Number of bytes immediately after the 32-byte header |
| 28 | 4 | payload CRC32 (`u32`) | CRC-32/IEEE of exactly those payload bytes; polynomial `0xEDB88320`, initial and final XOR `0xFFFFFFFF` |

The current reader checks magic, format version, declared payload length, and CRC before decoding the payload. It rejects truncated fields while decoding, a procedure whose line-info byte counts do not sum to its bytecode byte count, a shape table that does not begin with shapes 0 and 1, and a frame map whose captures' shape is not in the table or whose safepoints are not in ascending offset order within the bytecode. It does not validate the informational version, reserved field, unknown flag bits, trailing file bytes, or bytes remaining after the parsed payload. These are observations of version 16, not permissions for new writers to add data silently.

## Payload

`string` below means a `u32` byte length followed by that many bytes. The writer stores the bytes of its C++ strings; source paths and Marmot text are UTF-8 in normal compiler output. All counts are `u32`.

| Order | Field | Encoding |
|---:|---|---|
| 1 | entry source file | `string` |
| 2 | string pool | count, then that many `string` values |
| 3 | globals | count, then for each a name `string` and a kind `u8` |
| 4 | shapes | count, then for each a field count and that many `u32` field indexes |
| 5 | procedures | count, then the records below in index order |
| 6 | native libraries | count, then the records below in index order |
| 7 | embedded source files | Present only when header flag bit 0 is set; count, then the records below |

A kind is `1` for a value that is a heap object and `0` for one that is not. Nothing in the VM decides it from a value's bits. A shape lists the fields of a tuple, struct, union or closure that hold pointers, in ascending order. Shape 0 lists none and shape 1 only field 0, in every program; the reader rejects a table that does not begin with those two.

Each procedure is: name `string`; source-path `string`; bytecode byte count `u32`; exactly that many raw bytecode bytes; line-info count `u32`; then `(source line i32, byte count i32)` pairs; then its frame map. Line counts describe consecutive **bytes** in the bytecode stream, including operand bytes, not a count of logical instructions.

A frame map is: slot count `u32` and one kind `u8` per frame slot, parameters first, since a slot holds values of one kind for the whole procedure; the shape of the procedure's captures, `u16`, which every closure of it takes; then a safepoint count `u32` and, in ascending offset order, for each: the bytecode offset `u32` just after an instruction a collection can start after with temporaries on the frame's operand stack, a temporary count `u32` and one kind `u8` per temporary from the bottom, and the kind `u8` of the result the instruction pushes. Every call has one, for its caller while the callee runs and once its result is pushed, as do `CONCAT_ARRAY`, `CONCAT_TEXT` and `MAKE_CELL`. A frame at `JUMP_BACK`'s target holds its slots only, and one at a callee's entry after `TAIL_CALL` its parameters only, so neither has an entry. Procedure names use `name@module`; the bootstrap procedure name begins with `$module_bootstrap$` and the main procedure name with `$main$`.

Each native-library record is: library-name `string`; symbol count and symbol-name strings; hint-directory count and directory-path strings; `thread_safe` `u8`; `has_checksum` `u8`; and a checksum `string` when `has_checksum` is nonzero. The current reader treats any nonzero boolean byte as true. Hint directories are serialized source-derived paths, not an address or pointer to a loaded library.

Each embedded-source record is: source-path `string`; line count `u32`; then source-line strings split at LF. The LF is omitted; a preceding CR from CRLF input can remain in the stored line. The writer includes distinct procedure source paths for which it has source lines, in first-seen procedure order. Source files are optional; line-info and procedure source paths are present even when sources are not embedded.

## Instruction and builtin IDs

[`registry-v16.json`](registry-v16.json) freezes all 179 opcode IDs, their total encoded lengths in bytes (including the opcode), and all 109 builtin indexes with their FFI argument and return marshalling kinds. An opcode is one byte. Its numeric ID is its zero-based position in the opcode list; a builtin ID is its zero-based position in the builtin list. The builtin ABI version constant is `1`, but it is not a separate field in `.mmc`.

An instruction stream consists of its opcode byte followed by the number of operand bytes indicated by the registry. One-byte operands are unsigned unless the instruction defines an `imm8` signed immediate. Eight-byte integer and word constants use least-significant byte first; Float constants use the eight bytes of their IEEE-754 binary64 representation, least-significant byte first. Procedure and text indexes encoded in two bytes use low byte then high byte; global indexes use high byte then low byte. Two-byte jump offsets use low byte then high byte. The registry's `category` and optional `description` fields preserve the instruction grouping and operand notes previously maintained in `OpCodes.def`. These notes describe some instruction layouts; the remaining operand roles must be made explicit from the VM decoder before implementing a new writer.

The registry generates each project's private `OpCodes.def` and `Builtins.def` with `python scripts/dev.py generate-mmc`. The compiler builtin table contains only names and indexes; the VM table includes its argument and return marshalling kinds. Generated files are checked in, so either CMake project can build without Python or the other project. `python scripts/dev.py generate-mmc --check` detects stale outputs without writing them. The `.mmc` gate checks both generated-file freshness and their IDs against the registry, then exercises the frozen artifacts.

`CALL_FOREIGN_INDEXED` embeds a builtin table index; changing the table's order changes program meaning. Native foreign calls use the native-library records and a symbol name. `CALL_FOREIGN` carries how each argument is passed, which the compiler takes from the declared parameter types: two bits per argument from bit 0, `0` raw bits, `1` a C string for `Text`, `2` an array view for `Array<T>`. Its return kind is `0` raw bits, `1` a C string, `2` an array of values, `3` an array of C strings for `Array<Text>`, with bit 7 set when the array's elements are pointers, which only a builtin returning an array of values can make; `CALL_FOREIGN_INDEXED`'s return byte carries the same bit. Format 14 added the argument-kind byte; format 13's `CALL_FOREIGN` guessed each argument's kind from the value at run time.

Format 15 gave each value a kind and each aggregate a shape, so that nothing decides from a value's bits whether it is a pointer. The instructions that build objects or send values between workers carry them: `CREATE_ARRAY` its elements' kind; `CREATE_TUPLE`, `CONSTRUCT_STRUCT`, `CONSTRUCT_UNION` and `LOCAL_UNION2` a shape, low byte first, as their last two operands; `MAKE_CELL` and `CHANNEL_SEND` the value's kind; `SPAWN_WORKER` the shape of the tuple its arguments and function cross in, then the kind of the worker's result; and `JOIN_WORKER` the kind of the worker's value. A closure takes its procedure's captures' shape.

Format 16 took `JOIN_WORKER`'s four union tags away. The union it builds is the one its declaration in Marmot names, which the compiler checks by position: member 0 holds the worker's value and member 1 why there is none, itself a union of member 0 for a cancelled worker and member 1, holding the message, for a failed one. So the VM builds tags 0 and 1 without being told them. This file format carries the name, symbols, lookup hints, concurrency policy, and optional checksum, but not native machine code.

## Compatibility rule

Bump `format_version` when an existing artifact could otherwise be decoded or executed with a different meaning: changing field order or encoding, opcode IDs or operand layouts, builtin indexes or call semantics, or the meaning of an existing flag. Appending an opcode or builtin at the end need not renumber old entries, but the compiler and VM still need the same registry for the new entry. The producer's major/minor/patch header fields do not replace the format-version check.

[`fixtures.json`](fixtures.json) records the baseline compiler commit, source files, path normalization, expected VM behavior, and derivation of invalid artifacts. The committed fixture files deliberately use repository-relative paths so they are portable. The conformance check recompiles their sources, normalizes only serialized checkout paths, compares all remaining bytes, and runs the VM on the frozen artifacts.

Run the check with `python scripts/dev.py check mmc`; it also runs as the `mmc` step of `python scripts/dev.py gate`.
